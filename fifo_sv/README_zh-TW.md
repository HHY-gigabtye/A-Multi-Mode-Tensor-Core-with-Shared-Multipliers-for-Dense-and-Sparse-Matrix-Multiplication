# FIFO / Bridge Standalone Unit Verification

> Scope note: tool availability and verification statements below describe the original standalone delivery. See the [repository README](../README.md) and [source audit](../docs/source-audit.md) for later ModelSim and full-system verification.

This package verifies only `du_tc_bridge`. The testbench does not instantiate MLU, DU/TIA, Tensor Core, or MSU. Full-system integration verification follows successful standalone verification of each unit.

The standalone packaging revision changed the verification package and entry points, removing the partial-integration wrapper, integration testbench, integration scripts, and other units' RTL. `du_tc_bridge.sv`, `du_tc_bridge_pkg.sv`, and `tb_bridge.sv` retained their original versions. Hardware interfaces, timing, credit handling, and metadata behavior were unchanged.

## Running ModelSim / Questa

Extract the entire ZIP and preserve the `vectors/` subdirectory. In the Transcript, change to the `fifo_sv` directory and run:

```tcl
do run_bridge.do
```

You can also specify the full script path:

```tcl
do {C:/your_path/fifo_sv/run_bridge.do}
```

The script compiles four files in order and selects `tb_bridge` as the simulation top:

| Order | File | Purpose |
|---|---|---|
| 1 | `tensor_core_pkg.sv` | Shared packet types and constants; not the TC circuit |
| 2 | `du_tc_bridge_pkg.sv` | Bridge state, metadata, and FIFO entry types |
| 3 | `du_tc_bridge.sv` | The only hardware unit under test |
| 4 | `tb_bridge.sv` | Drives Bridge ports and checks results |

`tensor_core_pkg.sv` is retained because the FIFO uses its `tc_input_packet_t`. **Compiling the package does not instantiate Tensor Core.** This package does not include `tensor_core.sv` and runs independently of the TC circuit.

A successful run prints:

```text
BRIDGE RTL PASS: C-equivalent rows=19147 rejected_edges=7156 resets=13
```

Expected data are supplied in `vectors/bridge_vectors.txt`; ModelSim replay does not require running C or Python. The testbench uses ordinary `if` / `$fatal` checks, with no SVA or DPI. The original standalone environment ran Verilator; the ModelSim / Questa scripts had not been run at that delivery stage.

## Modeling External Signals Without Other Units

The testbench reads inputs and expected values generated by the original C model, then drives the Bridge boundary directly:

| Bridge port | Role in the unit test |
|---|---|
| `issue / issued_mode / issued_k / issued_meta` | Models an actual upstream issue into DU/TIA |
| `du_valid / du_packet` | Models DU/TIA output after four stages, without decoding hardware |
| `tc_accept` | Models downstream acceptance of the FIFO head, without matrix computation |
| `result_accept` | Models acceptance of a tile result and releases its metadata |
| `rst_n` | Clears Bridge state while the driver cancels pending events |

Every record compares status, all sideband/FIFO/metadata registers, counters, the head entry, and result metadata. Intentional contract violations expect a non-`IO_OK` status and verify that the entire Bridge state remains unchanged. A normally backpressured full condition is not an error.

`c_reference/` preserves the supplied original C model, headers, and standalone testbench, with only filenames restored for their includes. Their contents were not changed. The additional `generate_vectors.c` calls the original tests, adds randomized timing using four fixed seeds, and emits expected values. C structs and SV packed structs have different layouts; the generator converts fields explicitly rather than copying C memory.

## Unit Verification Coverage

- Consecutive inputs, input bubbles, and downstream stalls.
- FIFO occupancy up to 8, in-flight occupancy up to 4, and result metadata occupancy up to 2.
- Packet contents, ordering, k, tile ID, and 64-bit destination address.
- Same-cycle FIFO push/pop, same-cycle metadata push/pop, and pointer wrap.
- Missing credit, full metadata blocking a new tile, and DU timing/mode errors.
- Reset with in-flight data, FIFO data, or queued metadata; no stale data after restart.
- A total of 19,147 input/state records, including 7,156 expected rejected edges and 13 resets.

This verifies FIFO/Bridge functionality and cycle behavior. DU decoding, TC matrix computation, and actual end-to-end MLU/MSU handshakes belong to their unit tests and full-system integration.

## Preserved Hardware Behavior

The packet FIFO has 8 entries, the DU/TIA metadata sideband has 4 stages, and the result metadata queue has 2 entries.

`fifo_count + inflight_count <= 8`. `issue` reserves a credit; DU arrival transfers that credit from in-flight occupancy to the FIFO; only `tc_accept` releases it. `can_issue` uses current registered state, without same-cycle credit reuse.

DU output is written into the FIFO before TC can consume it on the following cycle. There is no payload bypass. The FIFO head is selected combinationally, without an extra output register.

When the head has `k=0` and result metadata is full, `head_valid=0`. Metadata is enqueued when TC accepts the first packet of a tile and dequeued on the **actual TC→MSU handshake**, without waiting for HBM writeback completion.

`side[]` is a physical four-stage tag pipeline holding only `valid / is_sparse / meta / k`. External DU/TIA logic processes the full arithmetic payload, which enters the FIFO only after DU/TIA output.

| Port | Meaning during integration |
|---|---|
| `can_issue` | Whether upstream may issue another packet into DU/TIA |
| `issue` | Actual issue into DU/TIA on this edge, not merely a request |
| `du_valid / du_packet` | Old DU/TIA S3 output; no ready port |
| `head_valid / head_entry` | Data currently eligible to enter TC |
| `tc_accept` | Actual FIFO→TC transfer on this edge |
| `result_meta_valid / result_meta` | Oldest unconsumed result metadata |
| `result_accept` | Actual TC→MSU transfer on this edge |
| `status` | Combinational indication of whether current inputs can commit at the next edge |

When the FIFO is nonempty, `head_entry` presents its head even if metadata blocking makes `head_valid=0`. Consumption requires both a valid head and TC readiness. An empty FIFO outputs zero.

Fields are `tile_id` (32 bits), `dst_addr` (64 bits), and unsigned `k` (8 bits, legal values 0..7). Mode is 2 bits: 0=dense, 1=hybrid, 2=dual, 3=illegal. The payload uses the existing packet type and preserves INT8 bit patterns directly.

**A normally full buffer causes a stall, not an error.** Upstream must wait when `can_issue=0`; asserting `issue=1` anyway produces `IO_NO_CREDIT`. Other statuses include `IO_BAD_FORMAT` and `IO_PROTOCOL_ERROR`. `IO_BAD_ARGUMENT` applies only to C NULL pointers and is not produced by RTL.

As in C, the Bridge does not commit an edge with non-`IO_OK` status. This diagnoses contract violations; it cannot pause external DU/TIA hardware. Integration must correct the source and reset the related modules together after such an error.

Upstream must guarantee eight packets per tile, ordered k=0..7, and consistent metadata within each tile. The Bridge preserves the C model's checking scope and does not add checks for these sequence rules.

## After Unit Verification

After each unit passes independently, connect the complete system. Start with a single tile in each of the three modes, then add consecutive tiles, input bubbles, and output stalls. A separate DU/TIA + FIFO + TC partial-integration test is not required first.

Reset DU/TIA, Bridge, and TC together and align the sideband with the actual four-stage DU/TIA latency. TC uses a strict valid contract: check its mode-aware `in_ready` before issuing, rather than only the current-mode `input_ready`. Keep the head packet connected to TC even when valid=0 so TC can inspect the next packet's mode.

## Rerunning on Linux

```bash
python3 run_tests.py
python3 run_tests.py --regenerate
python3 run_tests.py --trace
```

All three commands run only FIFO/Bridge. The first uses the supplied expected values; the second requires gcc and first reruns the original C model and tests; the third writes `bridge.vcd`. Simulation requires Verilator and a C++ compiler.

The script uses `-O0` to avoid incorrect constant folding of post-loop testbench statistics in the original environment's Verilator build. This affects only optimization of simulator-generated C++, not RTL. The script also retains the verified Linux/GCC precompiled-header settings.

The original standalone delivery did not run FPGA/ASIC synthesis or P&R and did not produce new Fmax, area, or power results.
